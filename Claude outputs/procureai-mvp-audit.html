Is the core loop actually good yet?

Ten checkpoints between “I need to buy X” and “X was purchased at a good price,” audited against the real code — not the vision. Three fixes show up in five checkpoints at once; those come first.

Three fixes, five checkpoints

These aren't in any single box below — they cut across the loop, and fixing each one once pays off everywhere it's cited.

1

The structured requirement dies after search

Extraction produces certifications, construction (“5-ply”), material, and pricing basis — but the RFQ record, the supplier's response form, and the quote comparison view only ever read the old flat fields (product, quantity, quality). None of the precision the buyer saw during matching survives to the people actually quoting.

Affects checkpoints 1, 6, 7, 8, 9, 10
2

The quote link has no authentication

A supplier's response link is /respond/{id}?vendor={number} — a plain, guessable integer, no per-invite secret. Anyone holding an RFQ link can submit or silently overwrite a quote as any invited supplier.

Undermines “human decides” at checkpoint 7
3

Performance data exists and is never used

The supplier schema already has rfqsReceived, ordersAwarded, onTimeDeliveryRate — and the RFQ store already has every RFQ, quote and award. Nothing connects them. This is the cheapest path to “learns from every transaction.”

Sets up checkpoints 3, 4, 9 for later intelligence
Checkpoint by checkpoint

What works, what's weak, what's missing

Audited directly against lib/extraction, lib/matching.ts, lib/store.ts, lib/scoring.ts, and the RFQ/respond pages — not the intended design.

01

Requirement understanding

P0
✓Span-based extraction with a real schema — quantity, unit, location, price basis, and structured specs (material, construction, certifications), each with a confidence level. 16 representative test cases pass.
△India-centric currency/location dictionaries; ambiguous dates (DD/MM) unresolved; no handling for a request naming two different products.
–No way for a buyer to see and correct the interpretation before it drives matching — whatever the parser produced is final.
→Persist the structured result past search (cross-cutting #1); add a one-screen confirm/edit step.
02

Supplier discovery

P1
✓Server-side search returns the full scored, tiered, reasoned result set; the structured requirement now actually reaches it.
△Discovery is a full-table scan and score, not an index — fine at 50 suppliers, won't hold at 500+.
–No incremental sourcing path and no way for a buyer to flag “we need more suppliers here.”
→Define a repeatable, per-category ingestion process; tie it to the fallback message (P1 #8).
03

Supplier relevance

P0
✓Request-dependent scoring with hard-requirement gating (location, certs, MOQ, price) and a strong/potential/weak/no-match tier — verified across 7 different requirement styles.
△Keyword overlap can be fooled by a homonym (“circuit boards” loosely matched “Angle Board”) — caught, downgraded to weak, but a real ceiling on pure keyword matching.
–No learning loop yet — matching doesn't use which suppliers actually got quoted or awarded to improve future ranking.
→Centerpiece of “genuinely relevant” — keep tightening as categories (P1) add real test surface.
04

Evidence & trust

P0
✓Evidence drawer with source/URL/date/confidence per field; an explicit “no public evidence available” state; confidence is computed, never hand-set.
△“Verified by ProcureAI” is a real badge in the UI, but nothing in the codebase can ever set a supplier to verified — currently permanent dead code.
–SupplierPerformance exists in the schema but is null for all 50 — nothing computes it from the RFQ history that already exists.
→Wire performance from real transaction history (cross-cutting #3) — nearly free, and it's the “learns from every transaction” thesis made real.
05

Match explanations

P1
✓Every score traces to a structured explanation — matched capabilities, unmatched requirements, per-field fit — rendered as plain ✓/⚠ reasons. Nothing fabricated.
△Reasons describe supplier data accurately but tersely (“Not confirmed: shipping, 5-ply”) rather than in a buyer's own framing.
–The reasoning for why a supplier was invited doesn't survive onto the RFQ — by comparison time, it's gone.
→Snapshot the match explanation onto the invited-supplier record; show it beside each quote.
06

RFQ creation

P0
✓Multi-supplier invite straight from comparison, clean per-supplier links, a buyer-facing spec with a “suppliers should provide” checklist.
△The spec both sides see is built from flat legacy fields — a precise structured requirement degrades to a generic “quality” tag list.
–No buyer-set response deadline (only each supplier's own quote-validity date); no email delivery — links are copy-pasted by hand.
→Same fix as checkpoint 1 — this is where its absence is most visible to a supplier.
07

Supplier quote submission

P0
✓Real commercial fields — price, MOQ, lead time, shipping, tax, payment terms, validity — with the RFQ spec shown for context.
△No spec-compliance field — a supplier has no way to confirm (or flag a deviation from) a required certification.
–No authentication. The link is /respond/{id}?vendor={number} — a bare, guessable id, no per-invite secret. Anyone with the RFQ link can quote as any invited supplier, or silently overwrite their quote.
→Per-invite secret token before this goes anywhere beyond an internal demo (cross-cutting #2).
08

Quote comparison

P1
✓Automatic price/lead-time/payment-terms scoring, a plain-language recommendation line, live polling as quotes arrive.
△Scoring is relative between quotes only — it never checks a quote against the buyer's actual stated ceiling or required specs.
–No flag when a quoted quantity undercuts what was asked, or conflicts with the supplier's own MOQ; assumes one line item.
→Reuse matching's hard-requirement model here instead of a separate, shallower score (cross-cutting #1 + #4).
09

Award decision

P1
✓One-click award from the ranked list; updates RFQ status; the UI hides re-awarding once one is made.
△“Reasoning” is one generic line, not the itemized evidence used earlier in matching — the loop's promise thins out right at the decision that matters most.
–No check against the buyer's hard requirements at award time (a quote missing the stated deadline awards with no warning); the API itself doesn't block a second award.
→Bring matching's evidence-based reasoning to the award screen; add a pre-award mismatch summary.
10

Purchase order generation

P2
✓PO number, computed totals (subtotal + tax + shipping), a delivery-by date from lead time, a clean summary view.
△If a supplier didn't quote a quantity, the fallback re-parses the buyer's original free-text string with a regex — duplicating work the structured extractor already did correctly.
–No downloadable or shareable PO document — it only exists as a record on the RFQ page, though it's the artifact a buyer actually needs to send onward.
→Correct once structured data flows through (checkpoint 1); a real exportable PO is the bigger open item.
Data strategy

The dataset is the other half of “relevant”

No matching algorithm invents evidence a supplier record doesn't have. Two separate gaps, and enrichment matters more than breadth right now.

0 / 50

Current suppliers with a public MOQ, price range, lead time, or certification on file. Every one is real (name, location, one sourced product line) — none can currently prove commercial or compliance fit, in any category.

Category Status Fields to prioritize Sourcing approach
Corrugated packaging 50 suppliers MOQ, price range, lead time, certifications — all currently null Re-visit existing 50 records; enrich from supplier storefronts, not just directory listings
Office furniture & fit-out 0 suppliers Products, capabilities, MOQ, lead time, industries served Same directory-sourcing discipline as packaging batch (IndiaMART-style, Bengaluru-first)
Electronics & components 0 suppliers Certifications (ISO 9001, RoHS), capacity, manufacturing status Higher compliance bar — prioritize sources that publish certs, not just product lists
Industrial equipment 0 suppliers Manufacturing capabilities, capacity, lead time Fewer, higher-detail records over volume — this category lives on spec fit
Raw materials & metals 0 suppliers Materials/grades (“304 stainless”), pricing basis, MOQ Grade-level product data matters more than company count here
Supplier performance (all categories) Schema only rfqsReceived, ordersAwarded, onTimeDeliveryRate — compute, don't source Derive from data/rfqs-store.json, which already has this history
Prioritized roadmap

P0 → P3

P0 makes today's loop trustworthy end to end. P1 gives it something real to work with. P2 and P3 are the intelligence and OS layers — not this milestone, listed for sequence.

P0
Make the core loop trustworthy
01
Carry the structured requirement through the whole RFQ recordPersist it at creation; show it on the RFQ spec, the supplier response form, and quote comparison — not just during search.
02

03
Compute supplier performance from real historyrfqsReceived, quotesSubmitted, ordersAwarded, on-time rate — from data already in the RFQ store.
04
Extend evidence-based reasoning into comparison and awardReuse the matching engine's hard-requirement model for quotes, not a separate, shallower price/lead-time-only score.
05
Add a requirement confirm/edit stepOne screen between “AI understood this” and “search suppliers” — the only point a parser mistake can still be caught before it reaches a PO.
P1
Make the data powerful
06

07

08

09
RFQ deadlines and real deliveryA buyer-set response deadline, and something better than copy-paste links.
P2

The loop already works end to end. It stops feeling like a demo the moment a buyer can trust every step of it — not just the first one.
